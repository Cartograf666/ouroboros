# Antigravity

Antigravity доступен ДВУМЯ путями, и они решают разные задачи. Ни один не
является API-провайдером и не проксирует OpenAI-совместимый протокол.

**1. Делегированный исполнитель через Claudexor (v6.101, основной путь).**
`agy` — полноценная цель делегирования: субагент со своей задачей, учётом
стоимости и накоплением статистики маршрута. Отсюда он попадает в раскладку
задачи (`propose_execution_plan`), которую утверждает владелец. Требует
Claudexor 3.5.0+, где живёт адаптер `agy`; текущий пин — 3.8.0.

**2. `antigravity_ask` — read-only консультация напрямую через CLI.** Дешёвый
второй взгляд внутри текущей задачи, без отдельного субагента и без Claudexor.
Запускается в режиме `--mode plan --sandbox`, поэтому не может ничего изменить.

## Где лежат креды

Это единственное место, где два пути расходятся принципиально, и разница
существенна для изоляции.

`antigravity_ask` вызывает CLI напрямую, поэтому Google OAuth остаётся там, где
его оставил вендор — в собственном хранилище `agy` и системном keychain
оператора.

Делегированный путь — нет. Адаптер Claudexor использует транспорт
`config_dir_login`: аккаунт живёт как ИМЕНОВАННЫЙ профиль внутри агентского дома
Ouroboros (`<data>/claudexor/profiles/agy-<id>`), со своим скоупленным `HOME`, а
переменные окружения с API-ключами затираются, чтобы не было тихого перехода на
метеред-тариф. Личный логин оператора при этом не читается и не импортируется.

У Antigravity НЕТ дефолтного аккаунта — это заявляет сам движок
(`default_credential: fail`, «accounts are named profiles»). Поэтому первый же
аккаунт заводится по имени, а не кнопкой Connect, и маршрут пиннится к нему
явно (`credentialProfileId`). Статус самого харнесса при этом навсегда остаётся
`unavailable`: он отвечает на вопрос про дефолтный credential, которого не
существует. Пригодность считается по вердикту движка о конкретном аккаунте —
см. `ouroboros/route_health.py`.

## Авторизация и проверка

Установка CLI:

```sh
curl -fsSL https://antigravity.google/cli/install.sh | bash
```

Проверка входа и списка доступных моделей:

```sh
agy models
```

Если CLI ещё не авторизован, Antigravity сам предложит пройти Google OAuth. В
Ouroboros ключ или refresh token для этого не задаётся.

Для ДЕЛЕГИРОВАННОГО пути нужен именованный профиль. Его можно завести из
Settings → Agents → Accounts (кнопка **Add account**, не Connect), либо
командой:

```sh
claudexor profiles add agy <id> && claudexor profiles login agy <id>
```

Учтите вендорское ограничение: код авторизации живёт около **60 секунд** с
момента открытия ссылки, продлить его нечем. Ссылка, код и окно ввода должны
быть из одного захода — код из старой вкладки даст `invalid_grant: Invalid code
verifier`, потому что PKCE-пара у каждого запуска своя.

Непройденный профиль лучше сразу выключить (`claudexor profiles disable agy
<id>`): проверка готовности перезапускает `agy` при каждом чтении статуса, а
неавторизованный CLI на это открывает окно браузера.

## Как пользоваться в чате

Попросите Ouroboros явно обратиться к Antigravity, например:

> Спроси Antigravity, насколько безопасен этот план миграции, и сравни ответ с
> твоим.

Внутри агент вызывает инструмент `antigravity_ask`. Можно указать `model` из
`agy models` и `effort` (`low`, `medium`, `high`). Каждый вызов запускается в
активном workspace с `--mode plan --sandbox`; файлы, коммиты и настройки не
изменяются.

## Что это не делает

Официальный CLI не предоставляет документированный OpenAI-compatible endpoint,
поэтому Antigravity не появляется как обычная модель в основном селекторе
Ouroboros или в Telegram. Это намеренное ограничение: добавление его туда через
перехват локального API/CSRF было бы неофициальным мостом и могло бы нарушить
условия OAuth-сессии. Полноценные длительные `start/wait/cancel` coding-runs
потребуют отдельного durable adapter; текущая интеграция безопасно закрывает
консультации, review, планы и улучшение промтов.
